# 요구사항 정의서 (Requirement)

프로젝트: 웹용 음료수 자판기 (간단한 쇼핑몰)
목적: 입문자가 풀스택 전체 구조(React → FastAPI → MariaDB)를 직접 하드코딩하며 이해하고 완성하는 학습용 프로젝트

---

## 1. 기술 스택 요구사항

| 영역 | 기술 | 비고 |
|------|------|------|
| 프론트엔드 | React.js (Vite) | 함수형 컴포넌트 + Hook |
| 백엔드 | FastAPI (Python 3.11+) | Uvicorn으로 실행, 자동 API 문서(Swagger) 활용 |
| 데이터베이스 | MariaDB 11.x | utf8mb4 문자셋 |
| DB 처리 | **ORM 미사용, SQL 직접 작성** | PyMySQL 드라이버 + 파라미터 바인딩 |
| 인증 | JWT (Access Token) + 비밀번호 해시(bcrypt) | |
| 통신 | REST API (JSON) | HTTP 클라이언트는 fetch 사용 |
| 실행/배포 | 로컬 PC 직접 실행 (Docker 미사용) | 5장 참고. 수강생 PC에 설치된 MariaDB 사용 |

### 1.1 프론트엔드 (React.js) 요구사항
학습 목표에 맞게 React의 핵심 개념을 **의도적으로 모두 사용**한다.

- **Hook 사용**
  - `useState`: 폼 입력값, 목록, 로딩/에러 상태 관리
  - `useEffect`: 화면 진입 시 API 호출(상품 목록 조회 등)
  - `useContext`: 전역 상태 공유
  - `useReducer`: 장바구니처럼 액션이 여러 개인 상태 관리
  - `useRef`, `useMemo`, `useCallback`: 필요한 곳에 최소한으로 사용
  - **Custom Hook** 작성: 예) `useFetch`, `useAuth`, `useCart`
- **State Lifting (상태 끌어올리기)**
  - 형제 컴포넌트가 같은 데이터를 쓸 때 가장 가까운 공통 부모로 상태를 올려 props로 전달한다.
  - 예) 상품 목록 ↔ 검색/필터 바, 관리자 상품 목록 ↔ 상품 수정 폼
- **Context API**
  - `AuthContext`: 로그인 사용자 정보, 토큰, 로그인/로그아웃 함수
  - `CartContext`: 장바구니 상태와 조작 함수
  - props drilling이 3단계 이상 깊어지는 데이터에만 적용한다. (남용 금지)
- **라우팅**: React Router (보호 라우트: 로그인 필요 / 관리자 전용)
- **구조**: 페이지(`pages/`) / 컴포넌트(`components/`) / 훅(`hooks/`) / 컨텍스트(`contexts/`) / API 호출(`api/`)로 분리한다.
- 상태 관리 라이브러리(Redux 등), UI 프레임워크는 사용하지 않는다. (순수 React 학습 목적)

### 1.2 백엔드 (FastAPI) 요구사항
- 계층 구조: `routers/`(요청·응답) → `services/`(업무 규칙) → `repositories/`(SQL 실행)로 분리한다.
- 요청/응답 데이터 검증은 Pydantic 스키마를 사용한다. (Pydantic은 ORM이 아니라 검증 도구)
- 인증/인가는 FastAPI `Depends`를 이용한 의존성으로 구현한다. (로그인 확인, 관리자 확인)
- CORS 설정, 환경변수(`.env`) 기반 설정 관리를 한다.
- API 문서는 `/docs`(Swagger)에서 확인할 수 있어야 한다.

### 1.3 데이터베이스 / SQL 요구사항
- **SQLAlchemy 등 ORM을 사용하지 않는다.** 모든 쿼리는 `repositories/`에서 SQL 문자열로 직접 작성한다.
- SQL Injection 방지를 위해 **반드시 파라미터 바인딩**(`%s`)을 사용하고, 문자열 연결로 SQL을 만들지 않는다.
- DB/계정 생성(`init.sql`), 테이블 생성(`schema.sql`), 초기 데이터(`seed.sql`)를 SQL 파일로 관리하고, 수강생 PC의 MariaDB에서 직접 실행한다.
- 학습 항목으로 다음을 직접 SQL로 다룬다: `JOIN`, `GROUP BY`(판매 통계), 트랜잭션(`COMMIT`/`ROLLBACK`), 외래키, 인덱스.
- 주문 처리(재고 차감 + 주문 저장)는 **하나의 트랜잭션**으로 처리한다.

#### 초안 테이블
| 테이블 | 주요 컬럼 |
|--------|-----------|
| users | id, email, password_hash, name, role(USER/ADMIN), status(ACTIVE/BLOCKED), created_at |
| products | id, name, price, stock, image_url, description, is_active, created_at |
| orders | id, user_id, total_price, status, created_at |
| order_items | id, order_id, product_id, quantity, unit_price |

## 2. 기능적 요구사항 (Functional Requirements)

우선순위: **필수(M)** / 권장(S) / 선택(C)

### 2.1 회원 / 인증 (사용자)
| ID | 요구사항 | 우선순위 |
|----|----------|----------|
| FR-A01 | 사용자는 이메일, 비밀번호, 이름으로 회원가입할 수 있다. | M |
| FR-A02 | 이메일은 중복될 수 없으며, 중복 확인 결과를 안내한다. | M |
| FR-A03 | 사용자는 이메일/비밀번호로 로그인하고 JWT를 발급받는다. | M |
| FR-A04 | 사용자는 로그아웃할 수 있다. (클라이언트 토큰 삭제) | M |
| FR-A05 | 비밀번호는 bcrypt 해시로 저장한다. | M |
| FR-A06 | 사용자는 내 정보(이름, 비밀번호)를 조회/수정할 수 있다. | S |
| FR-A07 | 차단(BLOCKED)된 회원은 로그인할 수 없다. | M |

### 2.2 상품 / 쇼핑 (사용자)
| ID | 요구사항 | 우선순위 |
|----|----------|----------|
| FR-P01 | 사용자는 판매 중인 음료 목록을 조회할 수 있다. (이름, 가격, 이미지, 재고 상태) | M |
| FR-P02 | 상품 이름으로 검색할 수 있다. | S |
| FR-P03 | 재고가 0인 상품은 "품절"로 표시하고 구매할 수 없다. | M |
| FR-P04 | 상품 상세 정보를 조회할 수 있다. | S |
| FR-P05 | 사용자는 상품을 장바구니에 담고, 수량 변경/삭제를 할 수 있다. | M |
| FR-P06 | 장바구니 내용은 새로고침 후에도 유지된다. (localStorage) | S |

### 2.3 주문 / 결제 (사용자)
| ID | 요구사항 | 우선순위 |
|----|----------|----------|
| FR-O01 | 로그인한 사용자는 장바구니 상품을 주문할 수 있다. | M |
| FR-O02 | 결제는 실제 PG 연동 없이 **가상 결제**(즉시 결제 완료)로 처리한다. | M |
| FR-O03 | 주문 시 재고가 부족하면 주문은 실패하고 사유를 안내한다. | M |
| FR-O04 | 주문 성공 시 재고가 차감되고, 주문/주문상세가 함께 저장된다. (트랜잭션) | M |
| FR-O05 | 사용자는 자신의 주문 내역과 상세를 조회할 수 있다. | M |
| FR-O06 | 주문 취소 시 재고가 복구된다. | C |

### 2.4 관리자 - 상품 / 재고
| ID | 요구사항 | 우선순위 |
|----|----------|----------|
| FR-M01 | 관리자는 상품을 등록/수정/삭제(또는 판매중지)할 수 있다. | M |
| FR-M02 | 관리자는 상품별 재고 수량을 조회하고 수정(입고)할 수 있다. | M |
| FR-M03 | 재고가 기준치(예: 5개) 이하인 상품을 별도로 표시한다. | S |
| FR-M04 | 상품 이미지는 URL 입력 방식으로 등록한다. (파일 업로드는 선택) | S |

### 2.5 관리자 - 판매
| ID | 요구사항 | 우선순위 |
|----|----------|----------|
| FR-S01 | 관리자는 전체 주문(판매) 내역을 조회할 수 있다. | M |
| FR-S02 | 기간별 / 상품별 판매 건수와 매출 합계를 조회할 수 있다. (SQL 집계) | S |
| FR-S03 | 관리자 대시보드에서 오늘 매출, 주문 수, 품절 상품 수를 요약해 보여준다. | C |

### 2.6 관리자 - 회원 관리
| ID | 요구사항 | 우선순위 |
|----|----------|----------|
| FR-U01 | 관리자는 전체 회원 목록을 조회할 수 있다. (검색/페이징) | M |
| FR-U02 | 관리자는 회원을 차단/해제할 수 있다. | M |
| FR-U03 | 관리자는 회원의 권한(USER/ADMIN)을 변경할 수 있다. | S |
| FR-U04 | 관리자는 회원별 주문 내역을 조회할 수 있다. | S |

### 2.7 권한 정책
| 구분 | 비로그인 | 일반 사용자 | 관리자 |
|------|:--------:|:-----------:|:------:|
| 상품 조회 | O | O | O |
| 회원가입 / 로그인 | O | - | - |
| 장바구니 / 주문 / 내 주문내역 | X | O | O |
| 상품·재고·판매·회원 관리 | X | X | O |

- 권한 없는 접근 시 백엔드는 401(미인증) / 403(권한 없음)을 반환하고, 프론트는 로그인 또는 안내 화면으로 이동시킨다.
- 최초 관리자 계정은 `seed.sql`로 생성한다.

### 2.8 화면 목록 (초안)
- 사용자: 메인(상품 목록), 상품 상세, 장바구니, 주문 완료, 내 주문내역, 회원가입, 로그인, 내 정보
- 관리자: 대시보드, 상품 관리, 재고 관리, 주문(판매) 관리, 회원 관리

## 3. 비기능적 요구사항 (Non-Functional Requirements)

### 3.1 학습성 / 유지보수성 (최우선)
| ID | 요구사항 |
|----|----------|
| NFR-L01 | 복잡한 로직보다 **구조의 명확함**을 우선한다. 한 파일/함수는 한 가지 역할만 한다. |
| NFR-L02 | 입문자가 이해할 수 있도록 핵심 코드에 **한글 주석**으로 "왜 이렇게 하는지"를 설명한다. |
| NFR-L03 | 구현은 `DB → 백엔드 API → 프론트 화면` 순서의 단계별 로드맵으로 진행하고, 단계마다 동작을 확인한다. |
| NFR-L04 | 불필요한 라이브러리를 추가하지 않는다. (직접 구현하며 원리를 이해하는 것이 목적) |
| NFR-L05 | 변수/함수/파일 명명 규칙을 통일한다. (Python: snake_case, React 컴포넌트: PascalCase) |
| NFR-L06 | 프로젝트 폴더는 `frontend/`, `backend/`, `db/`, `docs/`로 구분한다. |

### 3.2 보안
| ID | 요구사항 |
|----|----------|
| NFR-S01 | 비밀번호는 평문 저장/로그 출력을 금지하고 bcrypt 해시만 저장한다. |
| NFR-S02 | 모든 SQL은 파라미터 바인딩을 사용한다. (SQL Injection 방지) |
| NFR-S03 | JWT에는 만료 시간을 설정하고, 비밀키는 환경변수로만 관리한다. |
| NFR-S04 | 관리자 API는 서버에서 권한을 검증한다. (프론트 화면 숨김만으로 보호하지 않는다.) |
| NFR-S05 | CORS는 허용 출처를 명시적으로 지정한다. |
| NFR-S06 | `.env`, DB 비밀번호 등 민감 정보는 저장소에 커밋하지 않는다. (`.env.example`만 제공) |
| NFR-S07 | 로컬 학습 환경에서는 HTTP를 사용하며, HTTPS 적용은 확장 과제로 둔다. |
| NFR-S08 | 응답에 내부 오류 상세(스택트레이스, SQL)를 노출하지 않는다. |

### 3.3 성능
| ID | 요구사항 |
|----|----------|
| NFR-P01 | 목록 조회 API는 일반 조건에서 1초 이내에 응답한다. |
| NFR-P02 | 회원/주문 목록은 페이징 처리한다. |
| NFR-P03 | 자주 조회하는 컬럼(이메일, 주문 사용자ID, 주문일시)에는 인덱스를 둔다. |
| NFR-P04 | DB 연결은 매 요청마다 새로 만들지 않고 커넥션 풀을 사용한다. (권장) |

### 3.4 데이터 무결성 / 신뢰성
| ID | 요구사항 |
|----|----------|
| NFR-D01 | 외래키, UNIQUE, NOT NULL, CHECK(재고 ≥ 0) 제약으로 DB 레벨에서 무결성을 보장한다. |
| NFR-D02 | 주문 처리는 트랜잭션으로 묶어 중간 실패 시 전체를 롤백한다. |
| NFR-D03 | 동시 주문 시 재고가 음수가 되지 않도록 조건부 UPDATE(`WHERE stock >= %s`) 또는 행 잠금을 사용한다. |
| NFR-D04 | DB 데이터는 로컬 MariaDB에 보존하며, 백업/복원(`mysqldump`) 절차를 문서화한다. |

### 3.5 사용성 / 호환성
| ID | 요구사항 |
|----|----------|
| NFR-U01 | 최신 Chrome, Edge에서 정상 동작한다. |
| NFR-U02 | 모바일 화면 폭에서도 사용할 수 있는 반응형 레이아웃(CSS)을 적용한다. |
| NFR-U03 | API 호출 중 로딩 표시, 실패 시 사용자 친화적인 오류 메시지를 보여준다. |
| NFR-U04 | 입력값은 프론트에서 1차 검증, 백엔드에서 최종 검증한다. |

### 3.6 API / 오류 처리 규칙
- URL 규칙: `/api/v1/...` 접두사, 리소스 중심 명사 사용 (예: `GET /api/v1/products`)
- HTTP 상태코드를 의미에 맞게 사용한다: 200, 201, 400, 401, 403, 404, 409(중복/재고부족), 422, 500
- 오류 응답은 `{ "detail": "메시지" }` 형태로 통일한다.
- 로그: 요청/오류 로그를 터미널(콘솔)에 출력하여 확인한다.

## 4. 제약 사항 및 범위 제외
- ORM(SQLAlchemy, Tortoise 등) 사용 금지
- 실제 결제(PG), 배송, 이메일/SMS 인증, 소셜 로그인은 범위에서 제외한다.
- 이미지 파일 업로드, 주문 취소/환불은 선택 사항으로 후순위로 둔다.
- 대규모 트래픽, 다중 서버 확장(로드밸런싱)은 고려하지 않는다.

## 5. 배포(실행) 환경 요구사항

수강생 PC에 **MariaDB가 이미 설치**되어 있고 **Docker는 아직 학습하지 않았으므로**, Docker 없이 **로컬 PC에서 직접 설치·실행하는 방식**으로 구성한다. 별도의 서버 장비나 컨테이너 지식 없이도 전체 스택을 한 PC에서 실행·시연할 수 있는 것을 목표로 한다. (Docker 배포는 2단계 확장 과제로 둔다. 5.6 참고)

### 5.2 환경별 구성
| 구분 | 개발 모드 | 배포 모드 |
|------|-----------|-----------|
| 프론트 | `npm run dev` (Vite, :5173) | `npm run build` → `frontend/dist` 생성 |
| 백엔드 | `uvicorn app.main:app --reload` (:8000) | `uvicorn app.main:app --host 0.0.0.0 --port 8000` (`dist`를 함께 서빙) |
| DB | 로컬 MariaDB (:3306) | 로컬 MariaDB (:3306) |
| API 호출 | Vite 프록시(`/api` → :8000) 또는 CORS 허용 | 같은 주소 `/api` |
| 설정 | `backend/.env` | `backend/.env` (값만 운영용으로 변경) |

### 5.3 로컬 환경 요구사항
| ID | 요구사항 |
|----|----------|
| ENV-01 | 사전 설치: Python 3.11+, Node.js LTS, MariaDB(이미 설치됨), Git, VS Code |
| ENV-02 | Python 의존성은 가상환경(`python -m venv .venv`)에서 관리하고 `requirements.txt`로 기록한다. |
| ENV-03 | 프론트 의존성은 `package.json`으로 관리한다. |
| ENV-04 | DB 접속 정보(호스트, 포트, 계정, 비밀번호, DB명), JWT 비밀키, CORS 출처는 `backend/.env`로 주입한다. |
| ENV-05 | `.env`는 Git에 커밋하지 않고(`.gitignore`), `.env.example`만 제공한다. |
| ENV-06 | MariaDB 접속 계정은 root가 아닌 **프로젝트 전용 계정**을 만들어 사용한다. |
| ENV-07 | 포트 충돌에 대비해 백엔드(8000), 프론트 개발서버(5173), DB(3306)를 문서에 명시한다. |

### 5.4 DB 설정 요구사항
| ID | 요구사항 |
|----|----------|
| DB-01 | `db/init.sql`: 데이터베이스 생성(`utf8mb4`)과 전용 계정 생성·권한 부여를 담는다. |
| DB-02 | `db/schema.sql`: 테이블 생성 스크립트. 여러 번 실행해도 안전하도록 `IF NOT EXISTS` 또는 `DROP TABLE IF EXISTS`를 사용한다. |
| DB-03 | `db/seed.sql`: 관리자 계정과 샘플 상품 데이터를 넣는다. |
| DB-04 | 스크립트는 MariaDB 클라이언트(`mysql` CLI) 또는 HeidiSQL/DBeaver 중 수강생이 편한 도구로 실행한다. |
| DB-05 | DB 초기화(전체 재생성) 절차를 문서화하여 언제든 처음 상태로 되돌릴 수 있게 한다. |
| DB-06 | 백업은 `mysqldump`로 파일에 저장하고, 복원 절차도 함께 문서화한다. |

### 5.5 실행(배포) 절차 (요약)
1. MariaDB 서비스가 실행 중인지 확인한다.
2. `db/init.sql` → `db/schema.sql` → `db/seed.sql` 순서로 실행한다.
3. `backend/.env`를 작성한다. (`.env.example` 복사 후 값 수정)
4. 백엔드: 가상환경 활성화 → `pip install -r requirements.txt` → `uvicorn app.main:app --reload`
5. 프론트(개발 모드): `npm install` → `npm run dev`
6. 배포 모드 확인: `npm run build` 후 FastAPI를 실행하고 `http://localhost:8000`에 접속한다.
7. 회원가입 → 로그인 → 주문 → 관리자 기능 시나리오를 점검한다.
8. (선택) 같은 공유기/네트워크의 다른 기기에서 `http://내PC_IP:8000`으로 접속한다. 이때 Windows 방화벽의 8000 포트 허용이 필요하다.

### 5.6 확장 과제 (이번 범위 밖)
- Docker/Docker Compose 학습 후 컨테이너 배포로 전환 (Nginx + FastAPI + MariaDB 3컨테이너)
- 클라우드 서버(VPS) 배포, 도메인 연결, HTTPS(Let's Encrypt)
- Windows 서비스 등록 또는 프로세스 매니저로 상시 실행

### 5.7 목표 폴더 구조
```
VMFullStack/
├─ docs/            # 지시서, 요구사항, 가이드
├─ db/              # init.sql, schema.sql, seed.sql
├─ backend/         # FastAPI (routers / services / repositories), .env.example, requirements.txt
└─ frontend/        # React (pages / components / hooks / contexts / api)
```
